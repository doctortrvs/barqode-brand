# 03 — Design System

> This document defines the principles that govern Barqode's product interface.
>
> It is not a component library or UI kit. It defines how the interface should behave so every screen feels consistent, predictable and operational.

---

# Grid

Barqode uses a modular grid inspired by the rhythm of a barcode.

Layouts are built from consistent vertical and horizontal intervals that create predictable structure throughout the interface.

Like a barcode, the grid is repetitive, ordered and scalable.

The grid exists to create rhythm, not decoration.

---

# Shape

Barqode uses restrained geometry.

Shapes should feel engineered, precise and dependable.

Corners are softened only where they improve usability and approachability.

The interface should never feel harsh, but it should never feel playful.

Rounded corners exist to reduce visual friction—not to create personality.

---

# Actions

Actions should reflect priority.

Only the most important action on a screen should appear as a primary button.

Secondary actions should be visually quieter.

Tertiary actions should appear as links, contextual controls or menu items.

The interface should never present multiple competing primary actions.

When everything demands attention, nothing receives it.

---

# Density

Density should match the task.

Operational interfaces should maximise information density where speed and throughput are critical.

Decision-making interfaces should provide more space to improve comprehension and reduce cognitive load.

The interface should adapt to the user's objective—not apply a single density everywhere.

Density is a tool for productivity, not a visual style.

---

# Data Presentation

Data should be presented in the format best suited to the task.

Tables are the primary interface for operational work.

They are optimised for scanning, filtering, sorting and completing repetitive tasks at speed.

Cards are reserved for summaries, dashboards, KPIs and high-level information where comparison is less important.

We do not replace tables simply because cards look more modern.

Choose the format that enables the user to complete their task most efficiently.

---

# Navigation

Navigation should always provide orientation.

Users should know where they are, how they got there and where they can go next.

Every page should have a clear place within the system.

Navigation should feel like a well-organised warehouse.

Everything has an address.

Nothing feels lost.

The interface should never leave users asking:

> "Where am I?"

---

# Empty States

Empty states should guide users towards becoming operational.

They are not opportunities for entertainment.

They are operational checklists.

Every empty state should explain:

* Why this page is empty.
* What the user needs to do next.
* The fastest path to becoming operational.

Progress should be clear, actionable and measurable.

An empty system should never feel broken. It should feel ready.

---

# Errors

Errors should help users recover, not simply report failure.

Every error should answer three questions:

1. What happened?
2. Why did it happen?
3. What should I do next?

Technical implementation details should never replace operational guidance.

The user should always leave an error with a clear path forward.

The objective is not to explain the system.

The objective is to get the operation moving again.

---

# Findability

Information should always be easy to find.

Users should never have to remember where information lives.

Whether through navigation, filtering, search, recent activity or scanning, the fastest and most appropriate path should always be preferred.

Finding information should feel effortless.

---

# Final Principle

A great operational interface is not measured by how beautiful it looks.

It is measured by how quickly users can complete their work with confidence.

Every design decision should reduce friction, improve clarity and help the operation move forward.
